# Marionette 5.1 website and MCP release handoff

This is preparation, not evidence that 5.1.0 is published. Keep the website's
current 5.0.0 runtime and immutable MCP corpus unchanged until the gates below
have passed. Do not merge the announcement ahead of the release.

## Release input

- Library preparation: https://github.com/marionettejs/marionette/pull/3836.
- Obtain the final published source revision and registry readback from the
  release owner. A green preparation PR is not a registry receipt.
- Core, data, utils, radio and adapters must be 5.1.0 together. HTML and Router
  are optional, independently versioned packages. Do not rename them 5.1.0.
- Router 0.1.1 is the separately prepared docs/examples patch in PR3836. Its
  pre-v1 version is independent of core, not a work-in-progress label. Confirm
  its final published artifact and install instructions work with 5.1.0; fixing
  only the repository does not alter an existing npm tarball. Release owner
  reports runtime and types unchanged from 0.1.0. Do not present preparation
  as publication or pin provenance to an intermediate PR head.

## Runtime, documentation and MCP

1. Install exact published `marionette@5.1.0` and `@mnjs/data@5.1.0` as dev
   dependencies. Inspect the lockfile: data/utils/radio resolve to matching
   published 5.1.0 archives. Run a clean `npm ci`.
2. Run `npm run docs:stage-stable -- <certified-source-revision> 5.1.0`.
   This verifies archive integrity, installed bytes, source identity and docs
   digests. Preserve `output/stable-docs/stable-docs-evidence.json`.
3. Import the verified export with the README procedure. Reconcile every
   reading edit with the new immutable archive. Remove superseded edits and
   supplemental guides that the archive now includes. Never edit archive bytes.
4. Move `stableRelease` to 5.1.0 only with the real dependency and corpus update;
   reconcile `preparedRelease`, provenance and publication evidence together.
5. Rebuild the runtime and demo vendor bundles with the documented scripts.
   Check examples, workshop starter, installation snippets, package guides,
   agent setup, skills and downloadable projects. Preserve historical release
   references rather than blindly replacing every 5.0.x occurrence.
6. Run `npm run check`, `npm run test:browser`, `npm run test:docs:browser` and
   `npm run test:mcp:http`. Verify the MCP parity audit against the newly
   imported immutable corpus. Report actual document/example/resource counts,
   not the previous release's totals.
7. Inspect full desktop and narrow article, home/news entry points, package
   guides and installation examples. Verify links to both HTML and Router.

The MCP snapshot is generated from the same immutable imported archive, not
from website-only reading overlays. Verify the snapshot reports 5.1.0, its
certified source revision and digest. A website guide alone does not put that
guide into MCP. If a companion guide is absent from the published archive,
record that gap rather than silently changing the MCP provenance contract.

## Announcement and deployment

The promotional article introduces what HTML and Router let users build, keeps
optional installation explicit, and links to package guides and release notes.
Its publication date and hero image must be final before adding it to the news
feed. Release notes and article should share claims, not duplicate all detail.

Keep this work reviewable until Paul authorizes publication. Main merges deploy
both website and MCP through the established workflow. Do not use out-of-band
publishing. After approved deployment, verify the public website, MCP protocol
and resource provenance, then the configured Context7 refresh. A successful
build is not proof of deployed parity.
